# Architecture Freeze Review

**Дата:** 2026-08-01  
**Область:** финальная проверка архитектуры перед этапом Catalog.

> **Исторический контекст:** этот review отражает состояние документации на
> 2026-08-01. Последующая Documentation Cleanup устраняет отмеченные
> терминологические расхождения; документ не является источником текущего
> состояния архитектуры.

## Вердикт

К проектированию базовой Prisma-модели CatalogItem можно переходить только в
ограниченном контуре: без связей с PaymentLink, Transaction и Receipt, без
PaymentLinkItem, BookingItem и ownerId. Полный Architecture Freeze пока не
завершён из-за расхождений в ROADMAP и устаревших документах.

## Найденные проблемы

| Приоритет | Проблема | Рекомендуемое действие |
| --- | --- | --- |
| Высокий | ROADMAP не фиксирует ожидаемый порядок Calendar, Booking, Payment Links с несколькими позициями, Monetization, Users и Compliance. | Согласовать и явно зафиксировать порядок; автоматически не менять. |
| Высокий | `docs/ledger/LEDGER_AUDIT_VERIFIED.md` описывает simulate-payment как неатомарный, хотя текущий сервис использует `prisma.$transaction`. | Обновить audit или добавить отметку, что вывод заменён последующей реализацией. |
| Высокий | PROJECT_STATE и AGENTS не содержат `TransactionStatus.FAILED`, который есть в Prisma schema и используется webhook. | Документировать FAILED и уточнить смысл Transaction для неуспешной оплаты. |
| Средний | README и заголовок AGENTS используют устаревший термин «универсальная модель услуг». | Заменить на Catalog (CatalogItem). |
| Средний | Документация называет три модели монетизации, а Domain Model — две. | Зафиксировать две базовые модели: комиссия и подписка; HYBRID описать как их комбинацию. |
| Средний | API_V1, IA_AND_ROUTES_V1 и PRODUCT_SCOPE_V1 смешивают текущую и будущую функциональность без маркировки. | Пометить как целевые спецификации или архивировать после отдельного решения. |
| Средний | В Catalog Architecture category является одновременно ожидаемым полем и открытым вопросом; unit ограничен PRODUCT, но перечень единиц содержит SERVICE. | До Prisma-проектирования утвердить минимальный набор полей и устранить неоднозначности. |
| Низкий | В правилах Booking используется неописанный термин ServiceCatalogItem; точные правила буферов зафиксированы до проектирования BookingItem. | Использовать CatalogItem/SERVICE и отложить точные правила состава визита до Calendar and Booking. |

## Классификация сущностей

| Сущность | Ответственность | Тип | Реализована | Источник истины |
| --- | --- | --- | --- | --- |
| CatalogItem | Типовые параметры товара или услуги | Template | Нет | Будущая модель CatalogItem |
| PaymentLink | Предложение клиенту оплатить | Document | Да | Запись PaymentLink в БД |
| Transaction | Результат обработки платежа и финансовые значения | Fact | Да | Запись Transaction; остатки считаются по Ledger |
| LedgerEntry | Отдельное финансовое движение | Fact | Да | Ledger — источник финансовых остатков |
| Receipt | Состояние формирования чека | Document | Да | Запись Receipt для жизненного цикла чека |
| Calendar | Правила доступности времени | System | Нет | Будущая календарная модель |
| Booking | Конкретный визит клиента | Document | Нет | Будущая модель Booking |
| User | Владение данными и учётная запись | System | Нет | Будущая пользовательская модель |
| Monetization | Правила дохода платформы | System | Нет | Будущая конфигурация монетизации |

Минимальное изменение Domain Model: добавить в таблицу текущего состояния
столбцы «Тип» и «Источник истины».

## Snapshot

- Transaction и Receipt уже хранят собственные коммерческие значения, не
  вычисляя их из связанных объектов при чтении.
- CatalogItem пока не реализован и не связан с существующими документами;
  отдельный snapshot CatalogItem в коде пока не требуется.
- При реализации связей CatalogItem → PaymentLink и CatalogItem → Booking
  snapshot коммерчески значимых параметров обязателен.
- Модель передачи snapshot из состава продажи в Transaction и Receipt требует
  отдельного проектирования.
- User → CatalogItem и LedgerEntry не требуют snapshot CatalogItem.

## Открытые архитектурные решения

### MVP

- Порядок этапов в ROADMAP.
- Минимальный набор полей CatalogItem.
- Документирование TransactionStatus.FAILED.
- Типы сущностей и источники истины в Domain Model.
- Статус устаревших API, IA и scope документов.

### Post-MVP

- Модель PaymentLinkItem.
- Модель BookingItem.
- Порядок Booking и PaymentLink при предоплате.
- Общая или раздельная модель строк продажи и бронирования.
- Техническая реализация монетизации.
- Момент добавления User и ownerId.

### Future

- Учёт фактического времени и compliance.
- География, теги, медиа, вариации услуг и скидки.

## Оценка готовности

| Критерий | Оценка | Причина |
| --- | --- | --- |
| Domain Model | 3/5 | Ответственность и статусы описаны, но отсутствуют типы и источники истины. |
| Documentation | 2/5 | Основные документы согласованы, но есть устаревшие API/IA/scope и Ledger audit. |
| Ledger | 4/5 | Актуальный код использует атомарные операции; audit устарел. |
| Catalog Architecture | 3/5 | Границы и snapshot ясны, но набор полей и некоторые будущие правила не заморожены. |
| Roadmap | 2/5 | Не фиксирует ожидаемую последовательность Calendar, Booking и нескольких позиций PaymentLink. |
| Consistency | 2/5 | Есть расхождения по TransactionStatus, монетизации и устаревшим терминам. |

## Итоговая готовность

Базовый CatalogItem можно проектировать безопасно, если он остаётся независимым
шаблоном и не меняет финансовое ядро. До полного Architecture Freeze нужно
согласовать порядок ROADMAP, минимальный состав CatalogItem и перечисленные
документарные противоречия.

## Границы review

Код, Prisma schema и миграции не изменялись. Git add, commit и push не
выполнялись.
