# Итоги реализации Catalog MVP

Дата: 2 августа 2026

## Выполнено

### Prisma и база данных

Добавлена модель `CatalogItem` и миграция
`20260802081249_add_catalog_item`.

Реализованы типы:

- `SERVICE` — услуга;
- `PRODUCT` — товар.

Модель поддерживает утверждённые поля: название, описание, цену, категорию,
активность, параметры услуги, единицу измерения товара и правила предоплаты.

`ownerId`, пользователи, монетизация, Booking, PaymentLinkItem и snapshot-данные
не добавлялись.

### Backend API

Создан NestJS-модуль `CatalogModule` с контроллером, сервисом и DTO-валидацией.

Доступны endpoints:

- `GET /catalog` — список позиций, включая архивные;
- `GET /catalog/:id` — одна позиция;
- `POST /catalog` — создание;
- `PATCH /catalog/:id` — редактирование;
- `DELETE /catalog/:id` — мягкое архивирование.

Архивирование не удаляет запись из базы: оно устанавливает `isActive = false`.

В сервисе предусмотрены правила предметной области:

- у товара обязательно есть единица измерения;
- у услуги единица измерения отсутствует;
- товар не может быть доступен для записи;
- параметры длительности и буферов применяются только к услуге;
- фиксированная и процентная предоплата требуют значения;
- остальные режимы предоплаты не сохраняют значение предоплаты.

### Frontend

Добавлен экран `/catalog` с русским интерфейсом:

- список позиций;
- состояния загрузки и ошибки;
- создание;
- редактирование;
- архивирование с подтверждением;
- отдельные поля для услуг и товаров.

Экран использует API backend, а не `localStorage`. В нижнюю навигацию добавлен
раздел «Каталог».

### Документация

Документация синхронизирована с фактическим состоянием:

- базовая реализация `CatalogItem` отмечена как выполненная;
- `Catalog` уточнён как логическая совокупность `CatalogItem`, а не отдельная
  сущность;
- Calendar, Booking, пользовательская принадлежность, snapshots и связи с
  платежами сохранены как будущие этапы;
- следующий этап Roadmap — Calendar and Booking.

## Проблемы, которые требуется решить

### 1. Полная production-сборка frontend не завершается

**Проблема:** `pnpm --filter web build` останавливается при пререндеринге
существующей страницы `/payments/success`.

**Причина:** страница использует `useSearchParams()` без границы `Suspense`,
которую требует Next.js.

**Влияние:** production build web-приложения не может быть успешно завершён,
хотя код Catalog компилируется и проходит TypeScript-проверку.

**Рекомендуемое решение:** отдельно исправить
`apps/web/src/app/(app)/payments/success/page.tsx`, обернув компонент с
`useSearchParams()` в `Suspense` либо вынеся использование параметров в дочерний
client-компонент под `Suspense`.

### 2. Нужна ручная интеграционная проверка Catalog API

**Проблема:** HTTP-проверка CRUD не выполнялась в рамках реализации, потому что
порт `3001` уже занят существующим процессом backend.

**Влияние:** необходимо вручную подтвердить работу полного сценария в браузере
или через API: создание, редактирование, отображение и архивирование.

**Рекомендуемое решение:** определить владельца процесса на порту `3001`, затем
использовать текущий backend либо с явного разрешения перезапустить его и пройти
сценарий Catalog.

### 3. Нет автоматических тестов для правил Catalog

**Проблема:** правила нормализации и валидации `CatalogService` пока не покрыты
автоматическими тестами.

**Влияние:** при следующих изменениях выше риск случайно нарушить правила для
`SERVICE`, `PRODUCT` или предоплаты.

**Рекомендуемое решение:** добавить тесты сервиса для создания, обновления,
архивирования, отсутствующей единицы товара, запрета единицы у услуги и правил
предоплаты.

## Что не является проблемой

Следующие ограничения намеренны и должны оставаться до соответствующих этапов
Roadmap:

- нет `ownerId` и модели User;
- нет Calendar и Booking;
- нет нескольких позиций в PaymentLink;
- нет snapshot-данных;
- нет монетизации;
- нет авторизации и контроля доступа.

## Итог

Базовый Catalog MVP реализован и изолирован от будущих доменов. До начала
Calendar and Booking желательно устранить блокирующую проблему production-сборки
frontend и выполнить ручную интеграционную проверку API.
