## Этап 3. Ledger

Статус: выполнено.

Цель: создать единый журнал движения денег.

Проводки:

* поступление клиентского платежа;
* резервирование налога;
* резервирование комиссии платформы;
* зачисление остатка самозанятому;
* будущая выплата;
* будущий возврат;
* корректировки.

Реализовано:

* Ledger интегрирован в simulate-payment и payment.succeeded webhook;
* все четыре проводки создаются атомарно за одну Prisma-транзакцию;
* Dashboard использует LedgerEntry как источник истины для расчёта баланса;
* единая сервис-функция LedgerService.createTransactionEntries() унифицирует создание проводок.

## Этап 4. Catalog (CatalogItem)

Статус: выполнено для базовой реализации CatalogItem.

Добавить сущность `CatalogItem`.

**Архитектура описана в:** [docs/architecture/CATALOG_ARCHITECTURE.md](./docs/architecture/CATALOG_ARCHITECTURE.md)

### Два типа позиций

- **SERVICE** — услуга, участвующая в календаре и онлайн-записи
- **PRODUCT** — товар, не участвующий в календаре

### Поля CatalogItem

* id
* ownerId (пока отсутствует, будет добавлена на этапе Users)
* title
* description (опционально)
* type (SERVICE | PRODUCT)
* isActive
* isBookable (только для SERVICE)
* price (опционально)
* durationMinutes (только для SERVICE, опционально)
* bufferBeforeMinutes (только для SERVICE, по умолчанию 0)
* bufferAfterMinutes (только для SERVICE, по умолчанию 0)
* unit (только для PRODUCT)
* paymentPolicy (только для SERVICE, опционально)
* prepaymentValue (только для SERVICE, опционально)

### Planned import/export scope

P1: Catalog CSV export, create-only Catalog CSV import with preview/row
validation, and Booking CSV export by date range/status. P2: client import
after the Client domain exists and competitor-specific migration importers.
* category (опционально)
* createdAt
* updatedAt

### Важные архитектурные решения

- **CatalogItem ≠ конкретная продажа** — snapshot-модель фиксирует параметры в момент создания ссылки/записи
- **CatalogItem не знает о монетизации** — модель монетизации назначается пользователю, а не товару
- **CatalogItem не знает о Ledger** — финансовые расчёты выполняются независимо
- **Архивация через isActive** — удаления не производится, используется флаг архивации
- **Буферы используются только календарем** — не считаются длительностью услуги

### Связи

Связать CatalogItem с:

* платёжными ссылками (предполагаемая модель PaymentLinkItem);
* онлайн-записью (предполагаемая модель BookingItem);
* операциями (Transaction);
* чеками (Receipt).

## Этап 5. Календарь и онлайн-запись

Статус: Calendar MVP, Booking Core, Availability Core и Public Online Booking
выполнены. Calendar / Booking Management UI также выполнен. Следующий
подэтап — Notifications / Pilot UX hardening.

### 5.1 Управление графиком

* рабочие дни;
* рабочие часы;
* личные выходные;
* отпуск;
* государственные праздничные дни;
* официальные переносы выходных;
* ручное открытие или закрытие отдельной даты;
* исключения из базового графика.

Приоритет:

```text
ручное исключение
выше
государственного календаря
выше
недельного графика
```

### 5.2 Онлайн-запись

Реализовано:

* вычисляемая доступность через `GET /availability`;
* slots являются вычисляемым представлением Calendar, CatalogItem и
  CONFIRMED Booking и не сохраняются отдельно.

Остаётся:

* будущий business-specific public URL после добавления ownership/public profile.

Текущий `/book` — временный single-business public route MVP. Availability
вычисляется и не хранится в БД, а Booking Core остаётся финальной защитой от
пересечений. Внутреннее требование предоплаты и один связанный `Payment` уже
подключены; это не банковская Nominal Accounts интеграция.

### 5.3 Управление записью

Реализовано:

* owner routes `/bookings`, `/bookings/new` и `/bookings/:id`;
* ручное создание, перенос, отмена и завершение записи;
* snapshot-based Availability при переносе.
* transactional booking notifications and local/dev delivery dispatcher.

Остаётся:

* история изменений;
* notifications и Pilot UX hardening.

### 5.4 Оплата записи

Предоплата не обязательна.

Режимы:

* NO_PREPAYMENT;
* FIXED_PREPAYMENT;
* PERCENT_PREPAYMENT;
* FULL_PREPAYMENT.

При создании Booking политика и значение предоплаты сохраняются в BookingItem
snapshot. Требуемая сумма — сумма требований строк SERVICE: fixed ограничен
суммой строки, percent округляется `Math.round`, full равен сумме строки.
Ненулевое требование создаёт один Payment, а успешный существующий payment
lifecycle переводит отдельный Booking payment status в `PAID` и создаёт обычные
Transaction/Receipt/Ledger postings. Реальная банковская обработка и FNS/NPD
остаются отдельными будущими этапами.

## Этап 6. Монетизация платформы

Добавить сущности:

* MonetizationPlan;
* ClientMonetizationAssignment;
* BillingAccount.

Базовые модели:

### Commission (PERCENT)

Комиссия с клиентского платежа.

Деньги проходят через номинальный счёт.

Комиссия переводится с номинального счёта на расчётный счёт платформы.

### Subscription

Фиксированный ежемесячный тариф.

Самозанятый платит напрямую на расчётный счёт платформы.

Его клиентские платежи продолжают проходить через номинальный счёт.

При модели Subscription платформа установит platformFeeAmount=0 для клиентских платежей.

### Hybrid

Hybrid не является самостоятельной базовой моделью: это комбинация Commission
и Subscription.

Назначение тарифа:

* всем клиентам;
* сегменту;
* группе;
* отдельному клиенту.

Приоритет:

```text
индивидуальный тариф
выше
тарифа сегмента
выше
общего тарифа
```

T-Bank Nominal Accounts не предоставляют webhook для этих сценариев. Их sandbox
не хранит данные и не заменяет persistent E2E-тестирование. Подробности:
[T-Bank Nominal Accounts](./docs/architecture/TBANK_NOMINAL_ACCOUNTS.md).

## Этап 10. Чеки и налоговый контур

**P0 blocker:** Nominal Accounts не регистрируют чеки НПД/ФНС, а «Выплаты
самозанятым» не совмещаются с Nominal Accounts. До выбора отдельного compliant
provider/API, юридического и технического решения real-money pilot заблокирован.
Внутренний `Receipt` не является реальным чеком ФНС.

* PENDING;
* ISSUED;
* FAILED;
* CANCELLED;
* retry;
* externalReceiptId;
* история попыток;
* обработка ошибок.

## Финальный MVP

Самозанятый должен иметь возможность:

1. зарегистрироваться;
2. создать услуги;
3. настроить календарь;
4. разместить ссылку на запись;
5. принимать записи без предоплаты или с предоплатой;
6. создавать обычные платёжные ссылки;
7. принимать реальные платежи;
8. автоматически резервировать налог;
9. оплачивать комиссию или подписку;
10. формировать чеки;
11. видеть доступный баланс;
12. выводить деньги;
13. получать поддержку через админский контур.
