# CatalogItem Architecture

## 1. Назначение

**CatalogItem** — это позиция каталога товаров и услуг самозанятого, за которую клиент может заплатить.

В целевой архитектуре CatalogItem может использоваться как источник данных для:

- платёжной ссылки;
- будущей онлайн-записи;
- будущего Booking;
- аналитики;
- будущего каталога услуг.

CatalogItem не является фактом продажи, платёжным документом или финансовой операцией.

---

## 2. CatalogItem как неизменяемый бизнес-шаблон

CatalogItem хранит **типовые условия** товара или услуги. Это изменяемый
шаблон для будущих продаж и бронирований, а не продажа, бронирование, оплата
или финансовая операция.

- Может существовать годами без продаж.
- Цена, длительность и другие типовые параметры могут изменяться для будущих
  сценариев.
- Изменения не должны менять историческое содержание уже созданных
  PaymentLink, Booking, Transaction и Receipt.
- Исторические документы и операции должны использовать snapshot
  коммерчески значимых значений на момент создания.

На текущем этапе реализованы CatalogItem, PaymentLink, Transaction и Receipt.
Booking и модели состава документов ещё не реализованы; их связи и точный
состав данных относятся к целевой архитектуре.

---

## 3. Типы CatalogItem

На текущем этапе предусмотрены два типа:

### SERVICE

Услуга, которая может участвовать в онлайн-записи и занимать время в календаре.

Примеры:

- консультация;
- фотосессия;
- стрижка;
- ремонт;
- тренировка.

**Обязательные свойства SERVICE:**

- `title`
- `isActive`
- `type = SERVICE`

**Дополнительные свойства SERVICE:**

- `durationMinutes` — плановая длительность в минутах;
- `bufferBeforeMinutes` — подготовка до визита;
- `bufferAfterMinutes` — технический перерыв после визита;
- `isBookable` — может ли быть забронирована онлайн.

### PRODUCT

Товар, который не участвует в календаре и онлайн-записи.

Примеры:

- цифровой товар;
- консультационный пакет (без расписания);
- сертификат.

**Обязательные свойства PRODUCT:**

- `title`
- `isActive`
- `type = PRODUCT`

**Дополнительные свойства PRODUCT:**

- `unit` — единица измерения (PIECE, SET, HOUR и т.д.);
- `description`.

Архитектура должна допускать расширение списка типов без изменения общего
назначения CatalogItem. Новые типы не добавляются и не проектируются без
отдельного решения.

---

## 4. Полный состав полей CatalogItem

```
id
├─ ownerId (пока отсутствует, будет добавлена на этапе Users)
├─ title
├─ description (опционально)
├─ type (SERVICE | PRODUCT)
├─ isActive
├─ isBookable (только для SERVICE)
├─ price (опционально)
├─ durationMinutes (только для SERVICE, опционально)
├─ bufferBeforeMinutes (только для SERVICE, опционально, по умолчанию 0)
├─ bufferAfterMinutes (только для SERVICE, опционально, по умолчанию 0)
├─ unit (только для PRODUCT)
├─ paymentPolicy (только для SERVICE, опционально)
├─ prepaymentValue (только для SERVICE, опционально)
├─ category (опционально)
├─ createdAt
└─ updatedAt
```

---

## 5. Правила для SERVICE

### Свойства SERVICE

1. **title** — обязательное, название услуги.
2. **durationMinutes** — плановая длительность в минутах.
   - Может быть не задана.
   - Используется для бронирования и расчёта буферов.
3. **isBookable** — может ли быть забронирована онлайн.
   - По умолчанию `true`.
4. **bufferBeforeMinutes** — подготовка до визита.
   - Используется только календарем.
   - Не считается длительностью услуги.
   - По умолчанию 0.
5. **bufferAfterMinutes** — технический перерыв после визита.
   - Используется только календарем.
   - Не считается длительностью услуги.
   - По умолчанию 0.
6. **paymentPolicy** — правила предоплаты.
   - `NO_PREPAYMENT`
   - `FIXED_PREPAYMENT`
   - `PERCENT_PREPAYMENT`
   - `FULL_PREPAYMENT`
7. **prepaymentValue** — размер предоплаты (при наличии политики).

---

## 6. Правила для PRODUCT

### Свойства PRODUCT

1. **title** — обязательное, название товара.
2. **unit** — единица измерения (см. раздел "Единицы измерения").
3. **description** — опционально, описание товара.
4. **price** — опционально, типовая цена за единицу.
5. **isActive** — активен ли товар в каталоге.

### Ограничения PRODUCT

- PRODUCT не влияет на календарь.
- PRODUCT не участвует в онлайн-записи.
- PRODUCT не имеет durationMinutes, bufferBeforeMinutes, bufferAfterMinutes.
- PRODUCT не имеет paymentPolicy и prepaymentValue.

---

## 7. Правила цены

**`price`** — типовая цена.

### Правила

- Цена может быть не задана (null).
- Цена может отличаться в конкретной продаже.
- Фактическая цена должна сохраняться в snapshot создаваемого документа или
  операции; конкретная модель хранения ещё требует проектирования.
- **Transaction** всегда хранит фактическую сумму операции.
- **Изменение CatalogItem.price не влияет на старые документы.**

### Тип

```
price Int?  (в копейках/центах)
```

---

## 8. Правила длительности

**`durationMinutes`** — плановая длительность услуги (только для SERVICE).

### Правила

- Может быть не задана.
- Используется для:
  - резервирования слота в календаре;
  - расчёта доступных временных окон;
  - информирования клиента.
- Фактическое рабочее время будет храниться отдельно на уровне Booking.
- Изменение CatalogItem.durationMinutes не должно влиять на исторические
  бронирования; целевая модель snapshot для Booking будет спроектирована на
  этапе Calendar and Booking.

### Тип

```
durationMinutes Int?  (в минутах)
```

---

## 9. bufferBeforeMinutes

**`bufferBeforeMinutes`** — время подготовки ДО начала визита (только для SERVICE).

### Назначение

Техническое время, необходимое для подготовки к услуге:

- переодевание клиента;
- подготовка инструментов;
- дезинфекция помещения;
- переезд на место.

### Правила

- Используется **только календарем** для определения доступных слотов.
- **Не считается** длительностью оказания услуги.
- **Не суммируется** между несколькими услугами в одном визите.
- По умолчанию: 0.
- Если в визите несколько услуг с разными bufferBefore — используется **максимальное** значение.

### Формула расчёта занятого времени в календаре

```
Start = bookingTime - bufferBefore
Duration = bufferBefore + durationMinutes + bufferAfter
End = bookingTime + durationMinutes + bufferAfter
```

### Тип

```
bufferBeforeMinutes Int = 0  (в минутах)
```

---

## 10. bufferAfterMinutes

**`bufferAfterMinutes`** — время перерыва ПОСЛЕ окончания визита (только для SERVICE).

### Назначение

Техническое время между окончанием одной услуги и началом другой:

- дезинфекция помещения;
- оплата;
- подготовка к следующему клиенту;
- обеденный перерыв.

### Правила

- Используется **только календарем** для определения доступных слотов.
- **Не считается** длительностью оказания услуги.
- **Не суммируется** между несколькими услугами в одном визите.
- По умолчанию: 0.
- Если в визите несколько услуг с разными bufferAfter — используется **максимальное** значение.

### Формула расчёта занятого времени в календаре

```
Start = bookingTime - bufferBefore
Duration = bufferBefore + durationMinutes + bufferAfter
End = bookingTime + durationMinutes + bufferAfter
```

### Тип

```
bufferAfterMinutes Int = 0  (в минутах)
```

---

## 11. Правила онлайн-записи

**Только SERVICE может участвовать в онлайн-записи.**

### Правила

- PRODUCT не может быть забронирован онлайн.
- SERVICE с `isBookable = false` не отображается в интерфейсе записи.
- SERVICE с `isBookable = true` может быть выбран клиентом.
- При создании Booking клиент выбирает:
  - CatalogItem типа SERVICE
  - Дату и время (рассчитываются с учётом durationMinutes и буферов)
  - Количество (опционально)
  - Комментарий (опционально)

### Snapshot

Фактические параметры услуги на момент бронирования должны сохраняться как
snapshot. Предполагаемая модель состава Booking и набор её полей будут
уточнены на этапе Calendar and Booking.

---

## 12. Правила предоплаты

**Предоплата не обязательна.**

Для SERVICE поддерживаются режимы:

### NO_PREPAYMENT

Оплата полностью после услуги (по умолчанию).

### FIXED_PREPAYMENT

Фиксированная предоплата (сумма в поле `prepaymentValue`).

### PERCENT_PREPAYMENT

Процент от итоговой суммы (размер % в поле `prepaymentValue`).

### FULL_PREPAYMENT

100% оплата авансом, перед бронированием.

### Правила

- paymentPolicy может быть не задана (= NO_PREPAYMENT).
- prepaymentValue используется только если paymentPolicy требует суммы/процента.
- При создании Booking показывается размер предоплаты.
- Предоплата может быть сразу или запрос на оплату.

---

## 13. Единицы измерения

**`unit`** — единица измерения (только для PRODUCT).

### Поддерживаемые единицы PRODUCT

- **PIECE** — штука
- **HOUR** — час
- **MINUTE** — минута
- **DAY** — день
- **SET** — набор/комплект

### Правила

- Используется для отображения в платёжной ссылке и чеке.
- В целевой архитектуре может влиять на интерпретацию количества в составе
  платёжного документа или бронирования; окончательная структура этих
  моделей не утверждена.
- Например: 3 PIECE означает "три штуки"; 2 HOUR означает "два часа".

### Тип

```
type Unit = 'PIECE' | 'HOUR' | 'MINUTE' | 'DAY' | 'SET'
unit Unit
```

Для SERVICE единица услуги является неявной и не хранится в поле `unit`.

---

## 14. Snapshot-модель

При создании платёжной ссылки, бронирования, операции или чека, если они
содержат данные CatalogItem, коммерчески значимые параметры должны
копироваться в snapshot.

### Зачем

- Изменение CatalogItem не искажает историю цен, условий и услуг.
- Исторические документы не зависят от текущего состояния шаблона.

### Правило

Snapshot создаётся вместе с соответствующим документом или операцией.
Точные таблицы, поля и границы snapshot для ещё не реализованных моделей
не утверждены.

---

## 15. Предполагаемая модель PaymentLinkItem

Поддержка нескольких товаров и услуг в одной платёжной ссылке — принятое
продуктовое требование. PaymentLinkItem является предполагаемой моделью
строки платёжного документа и на текущем этапе не реализуется.

Возможная реализация должна хранить ссылку на выбранный CatalogItem и
snapshot коммерчески значимых условий. Конкретная структура PaymentLinkItem
не утверждена окончательно и требует уточнения после проектирования полного
жизненного цикла продажи, включая согласование с Booking, Transaction и
Receipt.

---

## 16. Предполагаемая модель BookingItem

Несколько товаров и услуг в одном визите — допустимый сценарий. Booking и
BookingItem пока не реализованы; BookingItem является предполагаемой моделью
состава бронирования.

На этапе Calendar and Booking будет определено, как состав визита влияет на
занятое время и оплату. Snapshot-подход обязателен, но конкретный состав
таблиц и полей пока не является окончательным.

---

## 17. Независимость от Ledger

**CatalogItem полностью независима от Ledger.**

### Правила

- CatalogItem не знает о LedgerEntry.
- CatalogItem не знает о налогах.
- CatalogItem не знает о комиссии платформы.
- При создании Booking или платёжной ссылки финансовые расчёты выполняются отдельно.
- Ledger получает готовый результат из Transaction.

---

## 18. Независимость от монетизации платформы

**CatalogItem полностью независима от модели монетизации.**

### Что CatalogItem не знает

- Commission (PERCENT, процентная комиссия)
- Subscription (фиксированный ежемесячный тариф)
- Hybrid как комбинация процентной комиссии и Subscription
- Правила назначения тариф

### Как это работает

1. CatalogItem задаёт только цену товара/услуги.
2. На этапе Monetization монетизация назначается **пользователю**, а не товару.
3. При создании платёжной ссылки или Transaction система:
   - Берёт цену из CatalogItem (или переопределяет вручную)
   - Применяет тариф пользователя
   - Рассчитывает налог и комиссию
   - Создаёт финансовые проводки в Ledger

### Правило

Изменение модели монетизации не требует изменения структуры CatalogItem.

---

## 19. Архивация через isActive

Удаления CatalogItem не должно быть в MVP.

### Вместо удаления

Используется флаг **`isActive`**:

```
isActive = false  →  позиция архивирована
isActive = true   →  позиция активна
```

### Правила

- Неактивная позиция не отображается в интерфейсе создания ссылки/записи.
- Неактивная позиция не мешает старым Booking и PaymentLink.
- Историческая информация должна сохраняться в snapshot документов и
  операций; конкретная модель строк пока не утверждена.
- Позицию можно переактивировать, установив `isActive = true`.

---

## 20. Ограничения текущего MVP

На текущем этапе:

1. **ownerId отсутствует** — система однопользовательская.
   - Будет добавлена на этапе Users.

2. **PaymentLinkItem не реализуется** — текущая PaymentLink не связана с
   CatalogItem. Поддержка нескольких позиций является продуктовым
   требованием, а модель её реализации ещё требует проектирования.

3. **Booking и предполагаемая модель BookingItem не реализуются** —
   окончательная структура будет определена на этапе Calendar and Booking.

4. **Предоплата не реализуется** — paymentPolicy и prepaymentValue используются для будущей функциональности.

5. **Категории опциональны** — не применяются в интерфейсе.

6. **Реализация развивается в порядке ROADMAP:**
   - CatalogItem вводится на этапе Catalog;
   - состав Booking проектируется на этапе Calendar and Booking;
   - модель нескольких позиций в PaymentLink требует отдельного
     проектирования жизненного цикла продажи;
   - ownerId добавляется на этапе Users.

## 21. Эволюция архитектуры

Утверждённый порядок определяется [ROADMAP.md](../../ROADMAP.md):

```text
Ledger
↓
CatalogItem
↓
Calendar and Booking
↓
Monetization
↓
Subscription Billing
↓
Users
↓
Bank Integration
↓
Receipts and tax integration
↓
Payouts
↓
Admin and operations
```

Поддержка нескольких позиций в PaymentLink развивается как часть эволюции
Sales and Payments; точное место реализации определяется после проектирования
жизненного цикла продажи. Каждый новый этап должен использовать уже созданные
компоненты и не требовать переписывания корректно реализованных предыдущих
этапов без отдельного архитектурного решения.

## 22. Открытые вопросы

### Календарь и работоспособность по географии

**Вопрос:** Нужна ли привязка CatalogItem к конкретному местоположению?

**Статус:** На уточнении.

**Влияние:** На этап Calendar. Возможно добавление поля `locationId`.

### Категории и теги

**Вопрос:** Нужна ли отдельная система категорий и тегов помимо опционального
поля `category`?

**Статус:** На уточнении.

**Влияние:** На фронтенд и каталог. Возможно добавление relation к `Category`.

### Медиа и фото

**Вопрос:** Может ли CatalogItem содержать фото услуги?

**Статус:** На уточнении.

**Влияние:** На фронтенд. Возможно добавление поля `photoUrl`.

### Вариации услуги

**Вопрос:** Может ли быть SERVICE с несколькими вариантами (например, стрижка короткая/длинная)?

**Статус:** На уточнении.

**Решение:** Скорее всего, отдельные CatalogItem с разными ценами и длительностями.

### Скидки и коды

**Вопрос:** Будут ли скидки на CatalogItem?

**Статус:** На этапе Monetization.

**Решение:** Скидки применяются при создании платёжной ссылки, а не в самом CatalogItem.
